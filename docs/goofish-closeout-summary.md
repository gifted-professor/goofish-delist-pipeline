# 闲鱼页面理解收尾摘要

日期：2026-06-22  
用途：作为本轮“先熟悉闲鱼页面”的短收尾。后续要继续自动化、多账号巡检、商品指标读取或交给别的机器时，从这份摘要进入即可。  
边界：本摘要只写页面级结论、风险类别和继续方式；不记录真实账号、店铺、订单、地址、聊天、商品标题、金额、经营数字、图片链接、二维码内容、验证码、cookie、token 或本地存储。

## 当前理解程度

- 已整理 66 个页面入口：31 个主站页面、35 个卖家工作台页面。
- 已按页面族、路由、入口方式、字段敏感度、控件风险、动作门禁、状态弹窗、页面流转和覆盖缺口建立索引。
- 当前登录 Profile 下，40 个页面已做只读 live 观察；8 个页面需要用户提供具体上下文；16 个页面只按静态证据解释；2 个页面是 shell/container 边界。
- 主站已确认首页、搜索、个人中心、收藏、买家订单、账号设置、发布、反馈、消息外壳、登录容器和更新页的结构边界。
- 卖家工作台已确认数据、商品、交易、财务、账号、客服、安全、推广、消息、下载、站点选择、账号检查、无权限等一级入口的结构边界。
- 页面理解可以支持只读巡检、页面分类、按钮风险判断、字段脱敏、账号/Profile 轮换和覆盖差异记录。

## 不能越过的边界

- 不主动触发支付、下单、确认收货、退款、发货、评价、投诉举证、保存、发布、导出、下载、上传、实名认证、账号找回、切号、发消息或权限变更。
- 不为了补覆盖制造订单、退款、发货、发票、认证、投放或聊天状态。
- 不拼真实订单、商品、用户、会话、地址、支付、发票、物流参数。
- 不保存或复制登录材料，也不把不同账号的登录态混到同一个 Profile。
- 列表、表格、订单卡、聊天、商品卡、财务和数据页面只记录字段名、tab、表头、按钮名、状态类别和风险等级。

## 多账号方式

推荐方式不是把密码、验证码、cookie 或 token 交给脚本，而是：

1. 每个账号使用一个独立浏览器 Profile。
2. Profile 只用别名，例如 `account-01`、`profile-a`。
3. 用户本人在对应 Profile 里完成扫码、验证码或登录。
4. 巡检脚本只读取页面结构和类别，不读取登录材料。
5. 不在闲鱼页面内主动点切号；切换账号通过切换 Profile 完成。

## 商品指标结论

本轮只读确认了一个关键问题：

| 场景 | 是否能稳定看到“想要” | 是否能稳定看到“浏览/浏览数” | 备注 |
| --- | --- | --- | --- |
| 自己的“我发布的”列表卡片 | 未稳定看到 | 未稳定看到 | 列表能看到商品卡和管理入口，但卡片层没有稳定暴露这两个指标 |
| 自己发布商品的详情页 | 可以看到相关信号 | 可以看到相关信号 | 详情页同时有编辑、下架、删除等管理入口，只能只读，不点动作 |

自动化建议：如果目标是统计自己发布商品的“想要”和“浏览数”，应从“我发布的”列表拿商品详情入口，再进入详情页只读抽取指标。是否记录具体数字，需要单独确认授权；默认只记录“可见/不可见”和字段类别。

## 最短结论

当前已经足够支持“登录一个账号后，只读理解闲鱼主站和卖家工作台页面，并设计多账号/Profile 巡检流程”。  
还不能宣称“所有隐藏/灰度/业务状态页面都已完整实测”，因为部分页面必须依赖真实订单、商品、用户、会话、权限、站点、售后、财务或平台灰度状态。  
下一步如果要进入实用自动化，优先做两个小闭环：多 Profile 只读覆盖对比，以及从自己发布商品详情页读取“想要/浏览数”指标。
